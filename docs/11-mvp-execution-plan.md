# EchoClass — MVP Execution Plan

> **Execution contract:** This is the plan for the next MVP implementation sprint. We will execute these steps in order and keep localhost:5173 working throughout. Do not jump ahead to CloudFront production hosting or unrelated product polish until the MVP flow is complete.

## 1. MVP Goal

Build a working EchoClass vertical slice that can run from the local Vite application while using real AWS services for identity and persistence:

```text
Browser (localhost:5173)
        |
        | Cognito authentication
        v
Amazon Cognito
        |
        | Bearer token
        v
API Gateway / Lambda
        |
        +------ DynamoDB (application data)
        |
        +------ S3 (private video objects)
        |
        +------ CloudFront (final private playback delivery)
```

The browser must never receive AWS IAM credentials, and video bytes must not be proxied through Lambda/API Gateway.

## 2. Current Baseline

Already working:

- React/Vite web application.
- Cognito signup, email confirmation, sign-in and logout.
- Student/Teacher registration identity.
- Authenticated route protection.
- Role-aware frontend routing.
- Local development at `http://localhost:5173`.
- Existing lesson/class UI foundations.

The old demo-session assumptions are no longer part of the execution plan.

## 3. Architecture Decisions for MVP

### Authentication

- Amazon Cognito remains the identity provider.
- Cognito `sub` is the immutable external identity key.
- EchoClass application user data is stored separately from Cognito.
- Student/Teacher role is authoritative in application data, not browser state.
- Backend authorization derives identity and role from the verified Cognito token and application-user record.

### Backend

Use AWS API Gateway HTTP API + Lambda functions.

Keep Lambda handlers domain-oriented rather than one giant handler. The first MVP handlers should cover:

- health/authenticated identity (`/me`)
- classes
- lessons
- upload authorization
- playback authorization
- Echoes

Use shared validation, error handling, authorization, and DynamoDB repository utilities.

### Database

Use DynamoDB as the application database.

Before creating indexes, document the exact MVP access patterns. Avoid designing a large generic relational-style schema. Prefer a small number of efficient access patterns and only add GSIs that are required by those patterns.

### Media

Use a private S3 bucket for original video objects.

- Block all public access.
- Enable encryption.
- Browser uploads directly to S3 using short-lived server-authorized upload URLs/permissions.
- Never upload video bytes through Lambda.
- Do not expose permanent public S3 URLs.

CloudFront is the final delivery layer. It uses Origin Access Control to reach the private bucket. Playback authorization is generated by the backend and is short-lived.

### Localhost strategy

`http://localhost:5173` remains the application origin throughout development.

Local development uses real AWS resources for Cognito, DynamoDB, Lambda/API Gateway, and S3. The browser only receives public configuration and short-lived authorization artifacts; AWS secrets/IAM credentials stay outside the frontend.

CloudFront production hosting is deliberately postponed until the local MVP works end-to-end.

## 4. Execution Order

### Phase A — Documentation and contracts

#### MVP-001 — Freeze MVP scope

- Use this document as the execution source of truth for the sprint.
- Do not start unrelated frontend polish.
- Keep each implementation change as a small PR.

**Done when:** this plan is merged and referenced by subsequent PRs.

#### MVP-002 — Define shared domain contracts

Define and validate the minimum entities:

- User
- Class
- Membership
- Lesson
- Echo
- Revisit (only if required by the first demonstrable flow)
- Upload/playback authorization response

**Done when:** the frontend and backend have stable, typed shapes for the MVP API.

---

### Phase B — AWS infrastructure foundation

#### MVP-010 — Establish AWS infrastructure project

Create the infrastructure-as-code foundation, preferably AWS CDK TypeScript, with configuration for the development environment.

Include:

- AWS region configuration
- environment naming (`dev`)
- resource naming conventions
- outputs for IDs/URLs needed by local development

**Done when:** infrastructure synthesizes successfully without deploying application code.

#### MVP-011 — DynamoDB table

Create the development application table.

First document these access patterns:

1. Resolve application user by Cognito `sub`.
2. Get class by ID.
3. List classes owned by a teacher.
4. Resolve student membership for a class.
5. List classes for a student.
6. Get lesson by ID.
7. List lessons for a class.
8. Verify student access to a published lesson.
9. Create/list/update/delete a student's Echoes for a lesson.
10. List lesson activity needed for MVP timeline/hotspot behavior.

Design PK/SK and only the required GSIs around these queries.

Enable encryption and appropriate development backup/recovery defaults.

**Done when:** the table exists and every MVP access pattern maps to a documented DynamoDB query rather than a scan.

#### MVP-012 — Private S3 media bucket

Create a development video bucket with:

- Block Public Access enabled.
- Server-side encryption enabled.
- No public bucket/object policy.
- Stable object-key convention derived server-side from application IDs.
- Optional lifecycle policy for abandoned uploads.

**Done when:** anonymous direct object access fails.

#### MVP-013 — CloudFront private media delivery

Create the final media delivery foundation:

- CloudFront distribution.
- S3 origin.
- Origin Access Control.
- Bucket policy allowing the CloudFront distribution, not the public internet.
- No direct public S3 access.

For local MVP testing, CloudFront may be provisioned before it becomes the default playback URL. The application must continue to work at localhost.

**Done when:** CloudFront can retrieve a test object while direct S3 access remains denied.

#### MVP-014 — API Gateway + Lambda foundation

Create:

- API Gateway HTTP API.
- Lambda runtime/build configuration.
- CORS for `http://localhost:5173`.
- CloudWatch logs.
- Least-privilege IAM permissions.

Start with an authenticated `/api/v1/me` or health endpoint.

**Done when:** localhost can call the API and receive a successful authenticated response.

---

### Phase C — Backend identity and data foundation

#### MVP-020 — Cognito token verification middleware

Lambda middleware must:

- Read the bearer token.
- Validate signature/issuer/audience and token type as appropriate.
- Extract Cognito `sub`.
- Reject missing/invalid/expired tokens.
- Attach authenticated identity to request context.

**Done when:** an authenticated request succeeds and an unauthenticated/tampered request receives 401.

#### MVP-021 — Application-user bootstrap

Create/resolve an EchoClass user record from Cognito identity.

Persist at minimum:

- internal user ID
- Cognito `sub`
- email
- display name
- role (`STUDENT` or `TEACHER`)
- created/updated timestamps

The backend must not trust a client-supplied user ID or role for authorization.

**Done when:** a real Cognito user can resolve to one application user.

#### MVP-022 — `/api/v1/me`

Return the authenticated EchoClass user and role.

Update the frontend auth bootstrap to use this endpoint as the application identity source rather than relying on demo-session assumptions.

**Done when:** refresh/login results in a backend-derived user and role.

---

### Phase D — Class and lesson APIs

#### MVP-030 — Class repository and APIs

Implement the minimum class operations:

- teacher creates class
- teacher lists own classes
- teacher gets/updates own class
- student lists enrolled classes
- student gets a class only when membership is active

Derive teacher/student identity from authentication.

**Done when:** cross-user class access is denied.

#### MVP-031 — Membership and invite code

Implement:

- teacher generates invite code
- student joins using invite code
- duplicate membership returns a controlled conflict
- teacher can view members
- removed membership no longer grants access

**Done when:** a teacher can create a class and a student can join it through the real API.

#### MVP-032 — Lesson repository and APIs

Implement minimum lesson lifecycle:

- teacher creates draft
- teacher updates metadata
- teacher publishes/unpublishes
- teacher archives
- student lists published lessons for an enrolled class
- student retrieves a published lesson

**Done when:** a student cannot access another class's lesson or an unpublished lesson.

---

### Phase E — Video upload and playback

#### MVP-040 — Upload authorization

Teacher requests upload authorization for a specific lesson.

Backend verifies:

- authenticated teacher
- lesson exists
- teacher owns the lesson's class
- upload policy (content type/size)

Backend derives the S3 key. Client cannot choose an arbitrary object path.

Return short-lived upload authorization.

**Done when:** the browser can receive authorization for a legitimate lesson and cannot authorize another teacher's lesson.

#### MVP-041 — Browser-to-S3 upload

From localhost:

1. Create/select lesson.
2. Request upload authorization.
3. Upload video directly to S3.
4. Report completion to backend.
5. Persist media metadata/status.

Lambda/API Gateway must never receive the video bytes.

**Done when:** a real video exists in the private bucket and the lesson records it as uploaded/ready.

#### MVP-042 — Playback authorization

Student requests playback for an authorized published lesson.

Backend verifies:

- authenticated student
- active class membership
- published lesson
- media exists and is ready

Return a short-lived CloudFront playback authorization mechanism.

**Done when:** the authorized student can play the video and unrelated users cannot.

#### MVP-043 — Local video lesson experience

Wire the existing lesson page to:

- fetch lesson metadata from API
- obtain playback authorization
- load the HTML5 player
- show useful loading/error/empty states

**Done when:** `http://localhost:5173` can open a real lesson and stream its private video.

### Phase F — Echo MVP

#### MVP-050 — Echo persistence

Implement DynamoDB repository and API for:

- create Echo
- list student's Echoes for a lesson
- update owned Echo
- delete owned Echo

Echo contains at minimum:

- ID
- student/application user ID
- lesson ID
- timestamp in seconds
- Echo type

**Done when:** ownership checks prevent cross-student modification.

#### MVP-051 — Echo composer + timestamp integration

On localhost:

- player exposes current timestamp
- student chooses Echo type
- optional note can be entered
- Echo is saved through API
- saved Echo appears in the lesson timeline/list
- selecting an Echo seeks the video to its timestamp

**Done when:** a student can watch → pause → Echo → save → revisit the exact moment.

#### MVP-052 — Echo edit/delete

Allow a student to edit/delete only their own Echoes.

**Done when:** ownership is enforced both in UI and backend.

## 5. What Is Explicitly Deferred

To keep the MVP sprint focused, these are not prerequisites for the first working release:

- Production frontend hosting.
- CloudFront distribution for the React application itself.
- CI/CD deployment automation.
- Multi-region AWS deployment.
- Advanced video transcoding/HLS pipeline unless browser playback requirements force it.
- AI-based hotspot detection.
- Advanced spaced-repetition algorithms.
- Social login.
- Complex teacher approval workflows.
- Full production observability/alerting.
- Offline support.
- Large-scale performance optimization.

CloudFront **for private video delivery** is part of the MVP because the media bucket must remain private; CloudFront **for hosting the web application** is deferred to the final deployment step.

## 6. Lambda Processing Policy

Lambda is used for application processing and authorization, not for transferring large video files.

Use Lambda for:

- authenticated API requests
- validation
- authorization
- DynamoDB persistence
- upload/playback authorization
- small deterministic analytics/revisit processing

Do not use Lambda to receive or return video bytes.

If video processing/transcoding becomes necessary, introduce an asynchronous media-processing service only after the basic direct-upload/private-playback path works.

## 7. Definition of MVP Complete

The MVP is complete when all of the following are true:

- Cognito authentication works.
- Student/Teacher identity works.
- Protected routes work.
- Application users are persisted in DynamoDB.
- Teachers can create classes.
- Students can join classes.
- Teachers can create/publish lessons.
- Videos upload directly from localhost to a private S3 bucket.
- S3 is not publicly readable.
- Authorized students can play videos through private delivery.
- Unauthorized users cannot access lesson/video data.
- Students can create timestamped Echoes.
- Students can edit/delete their own Echoes.
- Timeline/hotspot V1 works.
- Revisit V1 works if included in the acceptance path.
- No demo persistence remains in the MVP path.
- `pnpm --filter web build` succeeds.
- Backend/infrastructure validation and relevant tests pass.
- The complete acceptance scenario works from `http://localhost:5173`.

## 8. Execution Rules for This Sprint

1. **This document is the execution order.** Do not skip ahead because a later AWS service is interesting.
2. **Docs first, implementation second.** Update this document/state when scope changes.
3. **One coherent slice per PR.** Keep infrastructure and application changes reviewable.
4. **Localhost remains the primary acceptance environment.** Production hosting comes last.
5. **Real AWS services, no fake persistence for the MVP path.**
6. **Least privilege and private media are mandatory from the first implementation.**
7. **No AWS credentials in the browser.**
8. **No undocumented backend contracts.** Define contracts before consuming them.
9. **Build/test before merge.**
10. **Do not mark a task complete until its stated acceptance condition has been demonstrated.**
